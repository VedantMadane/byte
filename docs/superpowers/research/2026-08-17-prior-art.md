**Verdict: no project solves 80%+ of this.** Everything found either (a)
targets a single OS and hard-codes a native GUI toolkit, (b) swaps entire
config directories/files rather than surgically patching the two account-scoped
fields while preserving everything else, or (c) solves a different problem
(rate-limit-driven auto-rotation via a proxy, not manual account management).
None uses Rust, none abstracts secret storage across three platform backends,
none does atomic-write-with-backup-and-verify, and none does the sync-back
reconciliation in §7.1. This does not change the design; proceeding with the
existing plan. Worth noting for later: given how many similarly-named projects
exist, `byte`'s own README/positioning should make its cross-platform,
safety-first design explicit to differentiate it.

One incidental confirmation: Symbioose's README states plainly that "Claude

spec §2's note that macOS diverges from the JSON-file storage used elsewhere,
which is already why credential access sits behind a trait in §6.2. No new
finding; consistent with what the spec already documents.

### Deviation: `keyring`'s v3 feature names no longer exist

The brief's command (`cargo add keyring --features apple-native,windows-native,sync-secret-service`)
fails outright on the version that resolves today:

```
error: unrecognized features for crate keyring: apple-native, sync-secret-service, windows-native
disabled features:
    android-native-keyring-store, apple-native-keyring-store, cli, db-keystore
    dbus-secret-service-keyring-store, linux-keyutils-keyring-store
enabled features:
    v1, windows-native-keyring-store, zbus-secret-service-keyring-store
```

`keyring` has moved to a 4.x major release (this repo resolves 4.1.6) with a
rearchitected multi-backend feature system. Confirmed against the crate's own
`Cargo.toml` (fetched from `open-source-cooperative/keyring-rs`, the project's
current home — `hwchen/keyring-rs` now redirects there):

```toml
[features]
default = ["v1"]
v1 = [
    "apple-native-keyring-store/keychain",
    "windows-native-keyring-store",
    "zbus-secret-service-keyring-store",
]
```

Two things follow from this:

1. **Feature renames** (mechanical): `apple-native` → `apple-native-keyring-store`,
   `windows-native` → `windows-native-keyring-store`. There is no longer a
   feature literally named `sync-secret-service`; the Linux D-Bus secret-service
   backend now comes in two flavors, `dbus-secret-service-keyring-store` (built
   on the `dbus` crate, i.e. the old "sync" implementation using libdbus) and
   `zbus-secret-service-keyring-store` (built on the pure-Rust `zbus` crate, no
   system libdbus dependency). `zbus-secret-service-keyring-store` is the one
   the crate's own default feature set (`v1`) already selects, so it was used
   as the closest equivalent of the brief's "sync-secret-service" intent.
2. **`v1` is not just another backend — it's the compatibility-API feature.**
   Per the crate's own docs: *"If you enable the 'v1' feature, this library
   behaves essentially the same as the v1 version of Keyring behaved: it allows
   easy, platform-independent setting and reading of passwords/secrets on
   macOS, Windows, and \*nix platforms."* It is on by default and was left on
   (not disabled) because it already transitively pulls in exactly the three
   backends the brief asked for, and gives later tasks (Task 7: secret store)
   the same synchronous, single-store `Entry::new(service, user)` /
   `set_password` / `get_password` / `delete_credential` API that keyring v3
   exposed — which is almost certainly the API surface the spec was written
   against. The alternative (the new v4-native multi-store/async API) would be
   a materially bigger surface than this project needs.

Final `Cargo.toml` entry:

```toml
keyring = { version = "4.1.6", features = ["apple-native-keyring-store", "windows-native-keyring-store", "zbus-secret-service-keyring-store"] }
```

with default features (`v1`) left enabled. On Windows (this dev machine),
`apple-native-keyring-store` has no effect either way — its optional
dependency is gated to `cfg(any(target_os = "macos", target_os = "ios"))` in
keyring's own `Cargo.toml`, so it simply isn't part of the dependency graph
for this target regardless of the flag. It's kept explicit in `byte`'s
`Cargo.toml` so intent is documented for whoever builds on macOS, and so the
feature list survives if a future keyring release changes what `v1` implies.

No other crate's feature flags required adaptation — `serde`, `serde_json`,
`thiserror`, `anyhow`, `tempfile`, `time`, and `clap` all accepted the brief's
`cargo add` commands verbatim.

## Step 5 — `preserve_order` verification (critical)

This is the project's most important invariant: `serde_json::Value` must
preserve object-key insertion order, never re-sort keys alphabetically,
because `byte` patches two or three keys inside much larger JSON documents
(`~/.claude.json` is ~80 top-level keys) and must round-trip everything else
byte-for-byte.

Wrote the exact throwaway example from the brief to `examples/order_check.rs`:

```rust
fn main() {
    let v: serde_json::Value = serde_json::from_str(r#"{"zebra":1,"apple":2}"#).unwrap();
    println!("{}", serde_json::to_string(&v).unwrap());
}
```

Ran `cargo run --example order_check`.

**Observed output: `{"zebra":1,"apple":2}`**

This matches the input order exactly and is *not* the alphabetically-sorted
`{"apple":2,"zebra":1}` that plain `serde_json` (without `preserve_order`)
would have produced. `preserve_order` is confirmed active — it pulled in
`indexmap` as a transitive dependency (visible in the `cargo add serde_json`
output and in `Cargo.lock`), which is the mechanism `preserve_order` uses
under the hood (an `IndexMap`-backed `Map` instead of a `BTreeMap`).

The example was deleted immediately after (`examples/order_check.rs` does not
exist in the final tree; `examples/` is back to just its pre-existing
`.gitkeep`). No fix to `Cargo.toml` was needed — the feature was correctly
requested by `cargo add serde_json --features preserve_order` and is active.

### Open item 2 — refresh-token rotation (spec §7.1)

Decides whether §7.1's sync-back step is merely correct (current assumption)
or strictly necessary to prevent silently logging the user out by writing back
a rotated-out refresh token.

Run once, use Claude Code long enough for a token refresh to occur, then run
again and compare (never compare or log raw token values):

```bash
python -c "
import json,os,hashlib
p=os.path.expanduser('~/.claude/.credentials.json')
d=json.load(open(p))['claudeAiOauth']
print('refresh sha256[:12] =', hashlib.sha256(d['refreshToken'].encode()).hexdigest()[:12])
print('expiresAt =', d['expiresAt'])
"
```

If the hash changes between runs, refresh tokens rotate on use and sync-back
is load-bearing, not just belt-and-braces.
